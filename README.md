# CHOPA TECH — WiFi Billing, on Cloudflare Workers + D1

This is your WiFi hotspot billing system, rebuilt to run on Cloudflare
Workers with a D1 (SQLite) database and a real connection to your MikroTik
router. This README assumes no prior Cloudflare experience — follow it top
to bottom in order.

## What changed from the original build, and why

| Original | This build | Why |
|---|---|---|
| Express | [Hono](https://hono.dev) | Express needs Node's `http` module, which Workers doesn't have. Hono is built for Workers and has similar syntax. |
| Prisma + Postgres | Raw SQL over D1 (SQLite) | D1 is Cloudflare's built-in database — no external account needed. Prisma's D1 support exists but adds a fragile extra layer for a first deploy. |
| `node-routeros` (Node TCP socket) | Hand-written RouterOS API client over `cloudflare:sockets` | Workers can't use Node's `net` module, but it has its own native TCP socket API. See `src/integrations/mikrotik/`. |
| `bcryptjs` | Web Crypto PBKDF2 | bcrypt's deliberate CPU cost (~100-300ms/hash) eats Workers' per-request CPU budget fast, especially when generating many vouchers in a loop. PBKDF2 via Web Crypto is implemented natively by the runtime and is much faster here. |
| `jsonwebtoken` | [`jose`](https://github.com/panva/jose) | Built specifically for edge runtimes. |
| `winston` (file logs) | `console.log` | No filesystem on Workers — Cloudflare's dashboard captures console output as logs. |

Your frontend (`frontend/`) needed **no changes** — it already calls `/api/...`
as a relative path, so it works as-is once served from the same Worker.

## Before you start

You need:
1. A free [Cloudflare account](https://dash.cloudflare.com/sign-up)
2. **The Workers Paid plan ($5/mo)** — this is required specifically because
   outbound TCP sockets (`cloudflare:sockets`, used to talk to your MikroTik)
   are a paid-plan feature. Everything else here works on the free plan.
3. Node.js installed on your computer
4. Your MikroTik router's public IP (or DDNS hostname) and API port
   (default `8728`, or `8729` if you use the SSL API) reachable from the
   internet — which you already confirmed is the case.

## Step 1 — Install Wrangler and log in

```bash
npm install -g wrangler
wrangler login
```

This opens a browser window to connect Wrangler to your Cloudflare account.

## Step 2 — Install project dependencies

```bash
cd chopa-tech-workers
npm install
```

## Step 3 — Create the D1 database

```bash
wrangler d1 create chopa-tech-db
```

This prints a `database_id`. Copy it into `wrangler.toml`, replacing
`REPLACE_WITH_YOUR_D1_DATABASE_ID`.

## Step 4 — Run the database migration

This creates all the tables:

```bash
npm run db:migrate:local    # for local testing first
npm run db:migrate:remote   # for the real, deployed database
```

Optionally load two starter plans:

```bash
npm run db:seed:local
npm run db:seed:remote
```

## Step 5 — Set your secrets

Secrets are never committed to `wrangler.toml` — they're pushed straight to
Cloudflare individually:

```bash
wrangler secret put JWT_SECRET
# paste any long random string when prompted, e.g. generate one with:
# node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"

wrangler secret put ROUTER_CREDENTIALS_ENCRYPTION_KEY
# another long random string — this encrypts your MikroTik password at rest
```

If/when you connect a real payment gateway (M-Pesa etc.), also set:
```bash
wrangler secret put MPESA_CONSUMER_KEY
wrangler secret put MPESA_CONSUMER_SECRET
wrangler secret put MPESA_SHORTCODE
wrangler secret put MPESA_PASSKEY
wrangler secret put MPESA_WEBHOOK_SECRET
```
Until then, leave `PAYMENTS_MODE = "mock"` in `wrangler.toml` (the default) —
cash payments still work fully in mock mode; only mobile-money/gateway
payments are stubbed.

## Step 6 — Try it locally

```bash
npm run dev
```

Wrangler prints a local URL (usually `http://localhost:8787`). Note: local
`wrangler dev` **cannot** open real outbound TCP sockets to your MikroTik —
that only works once deployed to Cloudflare's network. Locally, any router
you add will fall back to the mock adapter automatically (see "Testing
without touching your real router" below).

## Step 7 — Deploy

```bash
npm run deploy
```

Wrangler prints your live URL, something like:
`https://chopa-tech-wifi-billing.<your-subdomain>.workers.dev`

Update `APP_URL` in `wrangler.toml` to match this, then redeploy
(`npm run deploy`) so links generated by the app point to the right place.

## Step 8 — Create your first admin account

Once deployed, register your account by calling the API directly (there's no
UI-only "first run" wizard, this is the safest one-time step):

```bash
curl -X POST https://<your-worker-url>/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"name":"Your Name","email":"[email protected]","password":"ChangeThisPassword123!"}'
```

The first account you register becomes an `ADMIN`. Log in through the actual
website after that. You can promote yourself to `SUPER_ADMIN` later via
`Staff` in the dashboard, or directly in D1:

```bash
wrangler d1 execute chopa-tech-db --remote \
  --command "UPDATE User SET role='SUPER_ADMIN' WHERE email='[email protected]'"
```

## Step 9 — Connect your MikroTik router

In the dashboard, go to **Routers > Add Router** and enter:
- Host: your router's public IP or DDNS hostname
- API port: `8728` (or `8729` for the SSL API — enable `useSsl`)
- Username / password: a RouterOS user with API access (**not** your
  everyday admin account — see the security note below)

The app tests the connection immediately using the real MikroTik adapter and
tells you if it fails, with troubleshooting tips (API service enabled,
firewall rules, credentials).

### Security note on the MikroTik user

Don't reuse your main admin login. In RouterOS:
```
/user group add name=api-only policy=api,read,write,!local,!telnet,!ssh,!ftp,!reboot,!password,!policy,!test,!winbox,!web,!sniff,!sensitive,!romon
/user add name=chopa-api group=api-only password=<a-strong-password>
```
Also restrict which IPs can reach the API port in **IP > Services**, if you
can pin down Cloudflare's egress ranges, or at minimum keep the port
firewalled to only what's necessary.

## Testing without touching your real router

Don't attach a real router to test the flow first. Add a router with
placeholder credentials, or none at all — if there's no stored credential
row for a router, the app automatically uses the mock MikroTik adapter
(clearly tagged `mock: true` in every response), so you can click through
voucher generation, payments, and sessions safely before pointing it at
production hardware.

## Known limitations / what's stubbed, honestly

- **M-Pesa (and other mobile money) live integration is a skeleton**
  (`src/integrations/payments/MpesaProvider.js`) — the exact request/response
  shape depends on your merchant agreement with Vodacom, which I don't have
  access to. `PAYMENTS_MODE=mock` works fully for demoing the flow; wire up
  the real calls once you have API docs and credentials.
- **SMS is mock-only** for the same reason — plug in your provider (Beem,
  Africa's Talking, etc.) in `src/integrations/sms/`, following
  `SmsProvider.js`.
- **Rate limiting** isn't implemented in-app (Workers isolates don't share
  memory the way `express-rate-limit` expects). Use Cloudflare's dashboard
  **Security > WAF > Rate limiting rules** instead — it's actually the
  better place for this on Workers, and doesn't cost you a Worker
  invocation.
- **Voucher batch size is capped at 500** (vs. the original's higher limit),
  because each voucher requires one MikroTik API round-trip inside a single
  request, and Workers has a CPU-time budget per request (raised to 30s in
  `wrangler.toml`, but not unlimited). For larger batches, either run
  multiple smaller requests, or convert `vouchers.js`'s generation loop into
  a Cloudflare Queue consumer later.
- **Money fields are stored as `REAL` (floating point)**, not fixed-point
  decimal, since D1/SQLite has no native decimal type. Fine for display; if
  exact accounting precision ever matters, switch these columns to `INTEGER`
  cents.
- **Password hash format changed** from bcrypt to PBKDF2 (see table above) —
  this only matters if you were trying to migrate an existing users table
  from the old Postgres database; a fresh D1 database doesn't care.

## Project structure

```
wrangler.toml           Cloudflare config: D1 binding, static assets, vars
migrations/0001_init.sql  Database schema
migrations/seed.sql       Optional starter plans
frontend/                Your existing frontend, unchanged
src/
  index.js               Hono app — mounts every route
  lib/                    db.js, password.js, crypto.js, jwt.js, voucherCode.js, audit.js
  middleware/             auth.js, errorHandler.js
  integrations/
    mikrotik/             protocol.js (RouterOS wire format), RouterOsAdapter.js, MockAdapter.js
    payments/             PaymentProvider.js, MockProvider.js, MpesaProvider.js (skeleton)
    sms/                  SmsProvider.js, MockSmsProvider.js
  routes/                 One file per resource — auth, dashboard, routers, plans, vouchers, ...
scripts/hash-password.mjs  Local helper to generate a PBKDF2 hash by hand
```
